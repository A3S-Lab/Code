状态：R0、I1 首批异步线程解阻塞，以及 E1 首批能力声明消费和宿主状态上下文已实现。

## 2. 设计约束和业界依据

1. **隔离与授权分别处理。** OS 后端限制文件、网络和进程；宿主的任务授权决定
   能否执行该操作。已授权且位于边界内的命令直接执行，新增资源才进入宿主授权。
   Claude Code 的官方文档同样将 sandbox 边界与 permission mode 分开。
2. **选择满足任务的后端。** 能力要求与实测能力匹配，不再用操作系统名称或
   “构造成功”作为可用依据。批准命令不能补足缺失的进程生命周期能力。
3. **搜索独立于索引。** VS Code 默认通过 ripgrep 搜索。Code 保留精确扫描作为
   结果依据，trigram 只缩小候选集；不要求先完成全库索引。
4. **过期工作可取消。** 参考 rust-analyzer 的后台请求和取消机制，更新到达后
   合并为最新需求；旧任务不能覆盖新版本。无需照搬其 panic/unwind 实现。
5. **后台工作有界。** Tokio 明确指出 CPU 密集的 blocking 工作需要并发限制，
   已启动的 `spawn_blocking` 无法靠 `abort()` 停止，因此必须协作取消并验证实际退出。

- [rust-analyzer 架构与取消](https://rust-analyzer.github.io/book/contributing/architecture.html#cancellation)

## 4. 关键行为契约

### 命令执行

- 会话开始执行一次有界的后端发现/探测；缓存按后端身份、策略和工作区失效。
  影响隔离的资源变更必须重新验证，不能复用过期成功结果。
- Bash、Python、构建工具和它们的子进程遵循同一个 OS 边界；不把 `python -c`、
  管道或命令名字当作安全分类器。
- 后端不可用：返回 typed unavailable 和具体缺项，零进程、零副作用。
- 资源被拒绝：返回确切路径或 origin、已有授权范围、可申请的最小扩展。
  已获授权的范围不重复确认。
- 进程已启动后失败或清理未知：保留退出与副作用证据，不自动换后端重跑。
  只有证明未启动，或有独立幂等/恢复依据，才能自动重试。
- 纯查询、执行 skill 和外部写操作分别声明真实能力；不能为了跳过观察把
  `Skill` 执行器或未知第三方工具统一声明为只读。输入 hooks 的副作用另行核算。
- 完成门禁错误必须携带原工具名、调用身份和具体缺失证据；不能只输出
  “1 invocation obligation”及让用户盲目重试。旧会话的欠账不得直接清空；
  恢复须绑定原调用及可信证明，不能把之后的 ls/搜索当作它已经结算。
- 联网安装必须验证网络中介；不能先关闭网络，再把无法下载当作工具失败。
  重定向涉及的新目标仍接受同一授权检查。
- 安装必须明确项目/用户受管目录的目标。Guest 内有文件不代表宿主安装成功；
  最终以宿主 Code 能发现并加载目标 skill 为准。受保护策略文件不因安装任务开放写入。

### 工作区索引

- 冷启动、构建中、失效、超预算、损坏时，精确搜索都能工作。
- 缺索引不能当作“无结果”。不确定的候选文件必须保留；缓存只允许假阳性，
  不允许因脏数据或未覆盖文件产生假阴性。
- 查询基于一致的版本，变更文件通过失效/脏文件覆盖处理。结果发出前按现有
  文件读取边界验证；跨版本、watcher 丢事件或更新竞态不能静默漏结果。
- 单文件读取使用预先的普通文件检查、打开后校验和实际读取上限；处理 FIFO、
  symlink/hardlink、文件增长与读失败。复用现有读取与 source-egress 边界。
- 索引预算独立于可搜索文件预算：大文件不入索引时仍走现有允许的精确读取路径，
  超过搜索大小限制的文件继续显式报告跳过。
- 索引只有在收益覆盖成本时才启用；限定文件/小目录的查询不触发全库构建。
  小工作区、频繁变更或预算压力下直接扫描是正常执行策略。
- 精确 grep、BM25 和语义检索的匹配语义分开；不通过静默切换模式提高“命中率”。
  模糊扩展只在既有契约允许时执行，并受整次请求剩余预算约束。
- 保留已有 catalog 文本/索引各 64 MiB 的预算；trigram 增加单文件、总索引、
  临时分配和并发预算。具体默认值在 E0 固定的基准上确定，同时测 RSS，
  不能把数据结构账面预算之和当成进程内存上界。
- 不添加每次任务都要求用户调整的索引开关；沿用宿主策略与现有 ACL 配置体系。

## 5. 初始性能目标

以下是待实现的验收目标，不是已测成绩。E0 先冻结机器、语料、计时起止点，
再记录是否达标；不通过缩小语料、隐藏排队/启动时间或放宽超时“优化”结果。

| 项目 | 初始门禁 |
| --- | --- |
| 不可用后端反馈 | 已完成会话探测后，准入拒绝 p95 ≤ 100 ms，实际进程数为零 |
| 限定范围搜索 | 最多 1,000 个文件、10 MiB 文本的基准，冷索引 p95 ≤ 1 s、热索引 p95 ≤ 200 ms |
| 大范围搜索 | 初始请求预算 10 s；超预算明确返回超时，不能输出完整零匹配或完整计数；更长任务由现有宿主预算授权 |
| 取消响应 | ACP 收到取消到确认 p95 ≤ 200 ms；本地正常文件上的后台索引停止 p95 ≤ 500 ms；命令树清理 p95 ≤ 2 s，未能确认时报告 unknown |
| 后台并发 | 先用一个后台 CPU 构建槽；每工作区一个构建和一个最新待处理需求；测量后再决定是否需要增加并发 |
| 对前台的干扰 | 同机交错开/关索引对照，选定主任务的 p95 增幅 ≤ 10%；后台任务压力下也满足前台延迟门禁 |
| 启动与预热 | 会话不等待全库索引；原生、Guest 冷启动、Guest 热启动及首次下载分别报告，全部进入真实任务总耗时 |

这些目标需要逐平台证明。无法承诺共享 CPU/磁盘下绝对零开销，因此以明确的
资源上限和前台延迟门禁兑现“不拖慢主任务”。
